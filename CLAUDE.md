# Правила работы над проектом

## Адаптивность — главное правило (приоритет №1)

Любая правка интерфейса сразу должна одинаково хорошо выглядеть и на телефоне, и на планшете, и на компьютере. Нельзя сделать красиво на компьютере и оставить «поплывшую» мобильную версию.

Перед тем как сказать «готово»:

1. Собрать демо (`npm run build:demo`) и сделать скриншоты изменённых экранов на ширинах **360, 390, 768 и 1440 px**.
2. Убедиться, что нет горизонтального скролла, ничего не обрезается и не налезает; сенсорные цели не меньше 44 px.
3. Посмотреть скриншоты глазами (телефон и компьютер) и приложить их к отчёту или PR.

Подробные критерии — в `ТЗ-и-план.md`, п. 12.

## Дизайн

- Цвета, тени и материалы — только через токены из `client/src/styles/tokens.css`.
- Два стеклянных материала:
  - **Liquid Glass** (`--lg-*`, классы `.lg`, `.lg-flat`) — прозрачное стекло для шапки и панелей.
  - **Frosted Glass** (`--fg-*`) — плотное матовое стекло как цифры часов на iPhone. Для главных плашек: переключатели, вкладки, нижняя панель, плитки меню «Ещё». Новые плашки этого типа делать на нём.
- Поле поиска и кнопку «Фильтры» стеклом пока не делаем — заказчик решил оставить как есть.

## Процесс

- Работать в отдельной ветке, в `main` напрямую не пушить, изменения — через PR.
- **Автослияние через GitHub Actions** (`.github/workflows/auto-merge.yml`, разрешено владельцем 20.10.2026): автопуш-хук Claude Code отправляет текущую ветку, workflow проверяет типы, сборку демо и серверные тесты (PostgreSQL в контейнере), сам создаёт PR и вливает его в `main`, затем запускает публикацию на Pages. Вручную вливать не нужно. Работать всё равно в отдельной ветке, не в `main`: прямой пуш в `main` минует проверку. Если проверка упала, в `main` ничего не попадает: смотреть вкладку Actions и чинить.
- Публикация автоматическая (решение заказчика): заказчик сам ничего не пушит и не вливает. После каждой законченной правки и проверки на 360/390/768/1440 самому закоммитить, отправить ветку в GitHub, создать PR и сразу влить его в `main`. Сайт на GitHub Pages собирается только из `main` (`.github/workflows/pages.yml`), пока правка не влита, на сайте её не видно.
- После вливания проверить, что сборка Pages прошла, и сказать заказчику, что на сайте обновилось. Если сборка упала — починить самому.
- Отвечать заказчику по-русски.

## Что важно помнить (обновлено 19.10.2026)

**Проект.** CRM сервис-центра Семёна. `shared` (схемы, роли, права), `server` (Express, pg, pdfmake, миграции `server/src/db/migrations/*.sql`, сейчас до `010`), `client` (React). Демо на GitHub Pages крутит сервер прямо в браузере на PGlite: база хранится в браузере заказчика, поэтому новые сотрудники и данные в старые базы попадают только через миграции или `bootDemo` (`client/src/demo/runtime.ts`). Подробные решения — в `ДОПУЩЕНИЯ.md` (п. 12, 29–33).

**Тесты и проверки.** Postgres 16: `service postgresql start`, затем `cd server && TEST_DATABASE_URL=postgres://postgres:test@localhost:5432/servicedesk_test npx vitest run` (сейчас 46 тестов). Типы: `npm run typecheck`. Интерфейс: `npm run build:demo`, `vite preview --mode demo --port 4173` (база `/website-for-semen`), Playwright с Chromium `/opt/pw-browsers/chromium`. Не использовать `pkill -f "vite preview"`. Prettier по всей папке трогает лишние файлы — форматировать только свои.

**Решения заказчика.**
- Рабочий день 10:00–19:00. Срок «Сегодня» — от текущего времени до конца дня, «Завтра» и «Послезавтра» — от начала до конца рабочего дня. Поле «Срок» остаётся.
- Комплектность: «Без ЗУ и кабеля питания» — одна кнопка, SIM не берём, «Карта памяти» остаётся.
- Квитанция: на каждое устройство лист A4 с двумя одинаковыми экземплярами (заказчику и сервису). Прежние «Условия» сохраняются, ниже «Примечание к заказу» из 15 пунктов, «С условиями договора, прейскурантом ознакомлен и согласен», дата, подписи. Общий лист на несколько устройств не делаем.
- Сотрудники: Семён, Стас, Ольга, Лёня, Артём, Матвей, Маша, Ваня. Исакова нет. Роли, угаданные нами, помечены «роль не уточнена» (`users.role_confirmed`).
- Роли: admin, manager, diagnostician, master, assistant («только задачи», у Вани), customer. Мастер и диагност видят только свои заявки и задачи (`orders.viewAll`, `orderAccess`, `taskAccess`), руководитель и администратор — всё. Права проверяются на сервере.
- Выезды: чек-лист работ клиента на вкладке «Выезд», график регулярных выездов (`service_plans`, задача ставится накануне), отдельный раздел «Выезды» в меню для всех сотрудников.

**Отложено заказчиком.**
- База данных и сервер: у заказчика свой сервер, PostgreSQL должна быть абсолютно отдельной базой (не от кассы столовой). Домен не нужен, для https нужен. Файл `servicedesk.sql` уже присылали, он не подходит для переноса как есть.
- Уведомления в Max: нужен токен бота, заказчик разберётся позже.
- Перенос контрагентов Семёна и Лёни: через импорт Excel, нужен сам файл.
