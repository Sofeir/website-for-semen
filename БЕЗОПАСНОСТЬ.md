# Безопасность сервиса: что проверено, что усилено, что осталось

Проверка 10.11.2026. Смотрел как человек, который ищет, через что сайт можно взломать: вход и пароли, права доступа, загрузка файлов, заголовки браузера, настройки сервера, зависимости.

## Что уже было хорошо (не менял)

- Пароли хранятся только в виде хеша (bcrypt), логин не выдаёт, существует ли такой сотрудник.
- Вход закрыт от перебора: 5 неудач на пару «адрес + логин» за 15 минут и 30 неудач на адрес.
- Вход держится на cookie, недоступной для скриптов страницы (HttpOnly, SameSite=Lax), идентификатор сессии в базе хранится только в виде хеша.
- Защита от подделки запросов (CSRF): проверка адреса отправителя и одноразовый токен на каждое изменение.
- Все запросы к базе идут с параметрами, без склейки строк: подстановка вредного SQL невозможна.
- Права проверяются на сервере: мастер не видит чужие заявки, заказчик видит только свой кабинет, помощник только задачи.
- Загруженные файлы: разрешён короткий список типов, проверяются первые байты (под .jpg не пройдёт программа), имена на диске случайные, отдаются с запретом выполнения.
- Базовые заголовки безопасности (CSP, запрет вставки в чужие страницы, HSTS при https), версия сервера в заголовках скрыта.
- Адрес клиента берётся из заголовка прокси, который прокси перезаписывает сам: подставить чужой адрес нельзя.
- Порт базы данных открыт только изнутри сервера.

## Что я усилил

1. **Пароли.** Хеш стал вдвое тяжелее для подбора (стоимость 12 вместо 10). Старые хеши пересчитываются сами при входе человека. Простые пароли (12345678, qwerty123, password, пароль с логином, из одних цифр и т. п.) не принимаются при регистрации, смене и создании сотрудника.
2. **Перебор пароля с разных адресов.** Раньше можно было пробовать пароль одного логина с сотни адресов по 5 раз. Теперь после 60 неудач за 15 минут попытки входа в этот логин идут по одной в порядке очереди, с промежутком 3 секунды, лишние параллельные получают отказ «подождите». Перебор упирается примерно в 20 попыток в минуту на логин и не обходится параллельными запросами. Вход при этом не закрывается: владелец повторяет попытку через несколько секунд.
3. **Потолки на частоту запросов.** Общий: 900 запросов в минуту на сотрудника (на адрес, если не вошёл). Тяжёлые действия (загрузка файлов, отчёты, документы, выгрузки): 60 в минуту. Регистрация: 20 в час с адреса. Лента календаря: 60 в минуту с адреса. Это останавливает заваливание сервера и массовый перебор.
4. **Cookie входа с префиксом `__Host-`** при работе по https. Браузер принимает её только по защищённому каналу, только на весь сайт и без домена. Подменить её с соседнего поддомена (на adminstart.ru есть другие сайты) нельзя.
5. **Сессии.** Просроченные входы теперь удаляются. Один человек может держать не больше 15 одновременных входов. Устройство при выходе перестаёт получать уведомления выходящего человека.
6. **Заголовки.** Ответы API не кэшируются браузером и прокси (`Cache-Control: no-store`). Запрещены микрофон, геолокация, платежи и USB (`Permissions-Policy`).
7. **Файлы.** К чужой заявке файл прикрепить нельзя (раньше можно было «подбросить» файл мастеру в чужую заявку).
8. **Экспорт в Excel/CSV.** Ячейки, начинающиеся с `=`, `+`, `-`, `@`, получают апостроф: вредная формула в названии клиента не выполнится в Excel у бухгалтера.
9. **Регистрация заказчика.** С одного телефона в очереди не больше двух заявок, не проверенные руководителем заявки удаляются через 30 дней, на адрес не больше 20 в час, общий потолок 500 заявок в очереди, руководителю уходит не больше 5 уведомлений о регистрации в час.
10. **Живые уведомления.** Не больше 10 открытых потоков на человека: один сотрудник не может занять все соединения сервера.
11. **Уведомления на устройство (Web Push).** Принимаются только адреса служб самих браузеров (Chrome, Firefox, Safari, Edge) по https. Иначе подписку можно было бы использовать, чтобы заставить сервер ходить по любым адресам, в том числе внутри сети.
12. **Зависимости.** Исправлены уязвимости в body-parser, multer, qs (отказ в обслуживании).
13. **Docker.** У контейнеров запрещено получать лишние права (`no-new-privileges`), у приложения убраны все особые возможности системы (`cap_drop: ALL`).
14. **Прокси Angie (применяется, когда Ваня включит домен скриптом `enable-domain.sh`).** Скрыта версия, отключены сессионные билеты TLS, запрет угадывания типа содержимого, вход и регистрация не чаще 30 запросов в минуту с адреса.

Проверка: 160 автоматических тестов проходят, в том числе новые на каждый из пунктов выше.

## Что осталось и почему

- **zod (библиотека проверки данных).** Известная уязвимость: огромные массивы могут съесть память. Исправление — переход на следующую версию библиотеки с переписыванием проверок во всём проекте. Риск сильно снижен: размер запроса ограничен 1 МБ, а частота запросов теперь ограничена. Переход стоит сделать отдельной задачей.
- **uuid внутри exceljs.** Уязвимость в функции, которую мы не используем. Исправление требует понижения exceljs до очень старой версии, это вредно. Оставлено.
- **Двухфакторного входа нет.** Для внутреннего сервиса приемлемо, но для директора и администратора стоит добавить (код из приложения или Max). Отдельная задача.
- **Ограничители частоты хранятся в памяти** и сбрасываются при перезапуске. Для одного сервера этого достаточно.
- **Приложение работает в контейнере от имени root.** Переход на обычного пользователя требует правки прав на тома с файлами на сервере; сделать может только Ваня.
- **Правки Angie не проверены на настоящем Angie** (на моём компьютере его нет). Скрипт `enable-domain.sh` сам проверяет настройки перед применением (`angie -t`) и откатывает их, если они не подходят.

## Осознанные компромиссы (решено оставить так)

- **Очередь входа при переборе логина.** Пока логин подбирают с разных адресов, лишние попытки получают отказ «подождите» ещё до проверки пароля. Проверять пароль у всех подряд нельзя: тогда параллельным перебором защиту можно обойти. Цена: владельцу в такие минуты иногда придётся повторить вход через несколько секунд. Полностью его не запирают. Если такое начнёт случаться, надёжное решение — двухфакторный вход или доверенные устройства (отдельная задача).
- **Потолок 500 заявок на регистрацию.** Если атакующий забьёт очередь с сотен телефонов и адресов, новые заказчики не смогут зарегистрироваться сами до тех пор, пока руководитель не разберёт очередь или не пройдут 30 дней. Взамен база не растёт без предела. Надёжное решение — подтверждение телефона по СМС (платный сервис).

## Что нужно сделать на сервере (Ване)

1. Закрыть на сервере всё, кроме портов 80, 443 и SSH (22): `sudo ufw default deny incoming && sudo ufw allow 22 && sudo ufw allow 80 && sudo ufw allow 443 && sudo ufw enable`. Проверить, что вход по SSH остаётся.
2. Вход по SSH только по ключу, без пароля и без входа root. Поставить `fail2ban` против перебора SSH.
3. Включить автоматические обновления безопасности системы: `sudo apt install unattended-upgrades`.
4. Файл `.env` должен быть доступен только владельцу: `chmod 600 .env`. В нём пароль базы и токены ботов.
5. Копии базы (`deploy/backup.sh`) хранить не только на этом же сервере, а ещё и в другом месте: если сервер взломают или он сломается, копии рядом пропадут вместе с ним. Периодически проверять, что копию можно развернуть.
6. После включения домена закрыть порт 50080.
7. Раз в месяц запускать `docker compose pull && docker compose up -d --build`, чтобы получать обновления образов базы и прокси.
