# Инструкция для Вани: что сделать на сервере

Здесь собрано всё, что нужно сделать на сервере, одним списком и по порядку. Три задачи:

1. убедиться, что новая версия сервиса приехала на сервер;
2. удалить тестовые заявки и задачи;
3. перевести сервис на домен `crm.adminstart.ru` с https.

Все команды выполняются на сервере, в папке проекта (по умолчанию `/opt/servicedesk`), от пользователя с правом `sudo`. Если команда `docker` не находится без `sudo`, пишите `sudo docker ...`.

Подробные описания лежат в файлах `ЧИСТКА-ТЕСТОВЫХ-ДАННЫХ.md` и `ДОМЕН-ПОШАГОВО.md`. Этот файл их дополняет: здесь порядок действий и шаги, которых там нет.

## Что должно быть готово до начала

- **Запись в DNS.** Семён добавляет в кабинете домена запись типа A: имя `crm`, значение `37.79.202.96`. Проверка: `nslookup crm.adminstart.ru` показывает `37.79.202.96`. Для шагов 1–3 DNS не нужен, для шага 4 нужен.
- **Порты на роутере.** Гриша Голенков пробрасывает входящие 80 и 443 (TCP) на этот сервер. Для шагов 1–3 порты не нужны, для шага 4 нужны.

Шаги 1–3 можно делать сразу, не дожидаясь DNS и роутера.

## Шаг 1. Проверить, что приехала новая версия

Сервер сам следит за веткой `release` и обновляется раз в минуту. Новая версия выложена, последний коммит `de7672d`.

```bash
cd /opt/servicedesk
git log --oneline -1
sudo docker compose ps
tail -n 20 /var/log/servicedesk-update.log
```

Ожидается: `git log` показывает коммит `de7672d` (или более новый), все три контейнера (`db`, `app`, `angie`) в состоянии `running`, `db` ещё и `healthy`, в журнале нет ошибок. Если версия не приехала, смотрите журнал `/var/log/servicedesk-update.log` и пришлите его последние строки. Дальше без этого не идите.

Заодно проверьте сайт: http://37.79.202.96:50080 открывается, вход работает.

## Шаг 2. Резервная копия

```bash
cd /opt/servicedesk
bash deploy/backup.sh
```

Запомните, куда сохранилась копия, и проверьте, что файл не пустой. Если копии делаются вашим способом, сделайте копию им. В новой версии добавлены миграции базы, которые применились при обновлении, поэтому копия нужна обязательно до любой чистки.

## Шаг 3. Удаление тестовых данных

Тестовые данные — это то, что осталось от начального наполнения базы: заявки с №001001 и по номер, с которого начинаются настоящие (ожидается около №001101), тестовые задачи (этапы тестовых заявок, выезды «РБЕ Урал», «Уральские технологии», «Кафе «Вкусно», разовые задачи вроде «Позвонить Игорю Котову…») и тестовые клиенты. Всё, что сотрудники завели за последнюю неделю, настоящее и должно остаться.

Заказчик разрешил удалить тестовые данные полностью, в том числе из отчётов. Порядок такой: сначала просмотр, вывод присылаете мне, я сверяю его со списком заказчика и подтверждаю границы, потом удаление.

**3.1. Просмотр задач** (ничего не удаляет):

```bash
cd /opt/servicedesk
sudo docker compose exec app npm run tasks:cleanup --workspace server
```

Скрипт показывает задачи группами по времени создания. Тестовые задачи — первая группа. Пришлите весь вывод.

**3.2. Просмотр заявок** (ничего не удаляет):

```bash
sudo docker compose exec app npm run orders:cleanup --workspace server
```

Скрипт показывает диапазон номеров и место, где нумерация переходит от тестовых заявок к настоящим. Пришлите весь вывод.

**3.3. Просмотр с границей.** Когда я подтвержу границы, будет ещё один просмотр, уже с параметрами, например:

```bash
sudo docker compose exec app npm run tasks:cleanup --workspace server -- --before "2026-10-28 00:00"
sudo docker compose exec app npm run orders:cleanup --workspace server -- --below 001101
```

Конкретные значения (дату и номер) я пришлю после просмотра 3.1 и 3.2. Если в списке есть хоть одна настоящая задача или заявка, не удаляйте и напишите мне.

**3.4. Удаление.** Только после моего подтверждения: те же команды с флагом `--delete` в конце. Сначала задачи, потом заявки. После заявок скрипт покажет клиентов без заявок. Тестовых клиентов я назову по номерам, удаляются командой:

```bash
sudo docker compose exec app npm run orders:cleanup --workspace server -- --clients 12,15,18 --delete-clients
```

**3.5. Проверка.** Откройте сайт под любым сотрудником: в разделе «Заявки» остались только настоящие, в «Аналитике» цифры по настоящим заявкам, настоящие задачи на месте. Если что-то удалилось лишнее, восстановите базу из копии шага 2 и напишите мне.

## Шаг 4. Домен и https

Делайте после того, как Семён добавил запись в DNS, а Гриша пробросил порты 80 и 443.

**4.1. Проверки перед запуском:**

```bash
# DNS указывает на сервер (в ответе 37.79.202.96)
nslookup crm.adminstart.ru

# порты 80 и 443 на самом сервере свободны или заняты только Angie из нашего проекта
sudo ss -ltnp | grep -E ':(80|443)\s'

# фильтр ufw (если он включён) пропускает 80 и 443
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
```

Если порты 80 или 443 на сервере занимает не наш `angie`, а что-то другое, не запускайте установку и напишите мне, что именно их занимает.

Дополнительно проверьте снаружи, не из локальной сети (например, с телефона через мобильный интернет), что http://37.79.202.96 открывает сервис. Если не открывается, проброс на роутере не работает или порт 80 закрыт у провайдера. Тогда напишите Грише и мне.

**4.2. Установка:**

```bash
cd /opt/servicedesk
sudo bash deploy/enable-domain.sh crm.adminstart.ru ПОЧТА
```

Вместо `ПОЧТА` — рабочая почта администратора. На неё Let's Encrypt присылает предупреждения, если сертификат перестанет продлеваться. Скрипт проверит DNS, выпустит бесплатный сертификат, включит https и перенаправление с http на https, пропишет в `.env` новые адреса (прежний сохранится как `.env.before-domain`), перезапустит приложение и поставит автоматическое продление. Можно запускать повторно. Если пишет, что DNS ещё не обновился, подождите и запустите снова.

**4.3. Проверка:**

```bash
curl -I https://crm.adminstart.ru/api/health
curl -I http://crm.adminstart.ru
sudo cat /etc/cron.d/servicedesk-certbot
```

Ожидается: первая команда отвечает `200`, вторая `301` с переходом на https, третья показывает задание продления сертификата. Затем откройте https://crm.adminstart.ru в браузере: вход работает, в адресной строке замок. Пришлите результат `curl`.

**4.4. Проверить продление сертификата** (пробный запуск, ничего не меняет):

```bash
sudo certbot renew --dry-run
```

**4.5. Закрыть старый адрес.** Когда новый адрес работает, попросите Гришу убрать на роутере внешний порт 50080.

**4.6. Проверить автообновление.** Сервис обновляется скриптом по расписанию. Убедитесь, что после установки домена он не сломался:

```bash
tail -n 5 /var/log/servicedesk-update.log
sudo docker compose ps
```

Настройки домена лежат вне репозитория, в `/etc/servicedesk-https`, и обновлением не затираются. Прежний `.env` лежит как `.env.before-domain`.

## Если что-то пошло не так

- **Скрипт домена остановился с ошибкой.** Сайт при этом продолжает работать по старому адресу (скрипт перед изменениями проверяет настройки). Пришлите последние строки вывода и `sudo docker compose logs --tail 30 app angie`.
- **Вернуть как было** (домен не нужен):

```bash
cd /opt/servicedesk
cp .env.before-domain .env
sudo rm /etc/servicedesk-https/crm.adminstart.ru.conf
sudo docker compose up -d --force-recreate app angie
```

- **Вернуть базу** из копии шага 2, если удалилось лишнее.

## Что прислать после выполнения

1. Результат шага 1: версия на сервере и состояние контейнеров.
2. Вывод просмотров 3.1 и 3.2 (до удаления).
3. После удаления: сколько задач, заявок и клиентов удалено (последние строки вывода).
4. Результат `curl` из шага 4.3 и подтверждение, что https://crm.adminstart.ru открывается.
5. Любые ошибки: текст целиком, без пересказа.

Пароли, ключи и содержимое `.env` в переписку не вставляйте.
